## Purpose

Provides authenticated Harbor execution plus repeatable, inspectable evidence of how Devcraft skills and hooks change agent behavior across supported hosts and workflow contexts.

## ADDED Requirements

### Requirement: Authenticated Harbor agent launch
The evaluation system SHALL use Harbor as its initial runner. It SHALL launch Claude Code with a user-supplied subscription OAuth token generated by `claude setup-token`, passed through the supported runtime environment variable. It SHALL launch Codex by setting Harbor's `CODEX_AUTH_JSON_PATH` to the user's host `auth.json`, allowing Harbor to upload only that file into its disposable secrets and Codex-home locations. Before running a trial, it MUST verify authentication from inside the same Harbor environment without printing, committing, or copying credential values into result artifacts. Missing, expired, or unsupported authentication MUST produce an actionable blocked result for that host.

#### Scenario: Reuse valid Codex authentication
- **WHEN** the evaluator supplies the host Codex authentication file
- **THEN** Harbor uploads only that file through its native Codex authentication path, verifies a minimal authenticated request, and records only the source path, transport mechanism, and status

#### Scenario: Reuse valid Claude authentication
- **WHEN** the evaluator supplies a Claude subscription OAuth token through the declared runtime variable
- **THEN** Harbor passes it only to the isolated Claude process, verifies a minimal authenticated request, and records only the authentication mechanism and status

#### Scenario: Clean up uploaded Codex auth state
- **WHEN** Harbor finishes or aborts a Codex trial using `CODEX_AUTH_JSON_PATH`
- **THEN** its temporary secrets directory and Codex home are removed without propagating changes to the host file

#### Scenario: Keep credentials ephemeral
- **WHEN** Harbor injects the Claude token or mounts or copies Codex authentication into an agent container or process
- **THEN** the credential contents are scoped to that runtime and are absent from committed configuration, normalized transcripts, and persisted results

### Requirement: One-shot and conversational launch modes
The Harbor scaffold SHALL support one-shot non-interactive execution and a persistent conversation with an agent under test. A conversation MAY use deterministic scripted messages or a testing agent that inspects each completed response and selects the next message while remaining blinded to the test arm and expected conclusion.

#### Scenario: Launch a one-shot CLI task
- **WHEN** a test declares one-shot interaction for Claude Code or Codex
- **THEN** Harbor runs the selected CLI non-interactively and captures its machine-readable events and final response

#### Scenario: Continue a scripted conversation
- **WHEN** a test declares fixed follow-up messages
- **THEN** the runner resumes the same logical agent session for each message and preserves turn order and session identity

#### Scenario: Continue with a testing agent
- **WHEN** a test declares an adaptive conversation policy
- **THEN** the testing agent can inspect the prior response and return either the next user message or a stop decision until a completion condition, turn limit, timeout, or failure is reached

### Requirement: Paired trial definitions
The evaluation system SHALL define control and treatment arms that start from equivalent task fixtures and differ only in declared Devcraft configuration. A trial definition MUST identify the agent host, model settings, initial fixture, interaction mode, enabled skills, enabled hooks, workflow context, timeout, and repetition count.

#### Scenario: Run a content-focused comparison
- **WHEN** an evaluator defines a control arm without a Devcraft skill and a treatment arm with that skill
- **THEN** the system runs both arms against equivalent fresh copies of the same fixture and records their declared difference

#### Scenario: Compare hook and skill effects independently
- **WHEN** an evaluator defines control, hook-only, skills-only, and hook-plus-skills arms
- **THEN** the system preserves those as distinct configurations whose outcomes can be compared independently

### Requirement: Verified agent configuration
The evaluation system SHALL configure each agent under test with the exact skills, hooks, workflows, and toolkits declared by its arm. Bootstrap smoke tests MUST use the subject's declared canonical installation or provisioning procedure. Direct skill or hook injection SHALL be sufficient for later content-focused behavioral evaluation. The system MUST fail the affected trial rather than silently continue when it cannot verify the declared configuration.

#### Scenario: Inject a skill directly
- **WHEN** a treatment arm declares a Devcraft skill and no marketplace installation
- **THEN** the agent under test can discover or invoke that skill through its native skill mechanism and the result records how it was supplied

#### Scenario: Reject incomplete setup
- **WHEN** a declared skill or hook cannot be placed where the selected agent will load it
- **THEN** the trial stops with a setup failure and produces no behavioral score

#### Scenario: Keep a candidate outside the marketplace
- **WHEN** a Devcraft skill has behavioral comparison fixtures but has not completed its promotion decision
- **THEN** its single source remains outside the published plugin payload and both host comparisons reference that unreleased source directly

### Requirement: Test-subject lifecycle
The evaluation system SHALL represent each tested skill, workflow, or toolkit with a minimal declaration of its canonical source and version, supported hosts, installation or provisioning action, required configuration, and use probe. Each installation smoke trial MUST start from a clean agent environment, verify discoverability after setup, perform the declared use probe, record source provenance, and discard the environment afterward.

#### Scenario: Install and invoke a subject
- **WHEN** a smoke trial selects a subject and a host that the subject declares as supported
- **THEN** the runner installs or provisions the pinned subject, verifies the host can discover it, invokes its minimal representative behavior, and records the evidence

#### Scenario: Reject a setup-only success
- **WHEN** installation exits successfully but the host cannot discover or invoke the subject
- **THEN** the smoke trial fails at the applicable verification or use stage

#### Scenario: Report an unsupported combination
- **WHEN** a subject does not support the selected host
- **THEN** the result records the combination as unsupported with its source evidence and does not count it as passed or silently skipped

### Requirement: Bootstrap installation-and-use suite
The first executable suite SHALL cover the Devcraft status skill, Superpowers, GSD, the Pocock skill collection, OpenSpec, and Spec Kit. It SHALL attempt each subject against both Claude Code and Codex, subject to the explicit unsupported-result rule, before the behavioral A/B corpus is considered ready.

#### Scenario: Use the Devcraft status skill
- **WHEN** the status-skill smoke test runs on a supported host
- **THEN** it installs the skill from this repository and verifies that an invocation returns recognizable Devcraft status or version output

#### Scenario: Exercise a third-party toolkit
- **WHEN** a Superpowers, GSD, Pocock, OpenSpec, or Spec Kit smoke test runs on a supported host
- **THEN** it installs a pinned canonical source and completes a minimal toolkit-specific invocation rather than merely checking for files

### Requirement: Headless and conversational behavioral execution
After bootstrap, the evaluation system SHALL support single-prompt headless trials and multi-turn conversational behavioral trials using the same launch mechanisms. In a conversational trial, a testing agent SHALL be able to inspect each response from the agent under test and issue the next test-controlled message until a declared completion condition, turn limit, timeout, or failure is reached.

#### Scenario: Execute a simple headless task
- **WHEN** a trial declares headless interaction with one prompt
- **THEN** the system runs the agent non-interactively and captures its machine-readable event stream and final response

#### Scenario: Exercise an evolving decision
- **WHEN** a conversational trial tells the agent under test an initial fact and later supplies evidence that changes it
- **THEN** the testing agent can continue the same logical conversation and the evaluation can inspect how the agent revises the decision

#### Scenario: Bound an unproductive conversation
- **WHEN** the conversation reaches its turn limit or timeout without satisfying the completion condition
- **THEN** the system ends the trial and records the applicable termination reason

### Requirement: Isolated and repeatable execution
Each trial SHALL run in a disposable workspace with a known initial state and MUST NOT depend on undeclared user skills, hooks, instructions, plugins, or workflow configuration. The system SHALL support repeated paired trials and SHALL retain agent, model, harness, and Devcraft version provenance for every result.

#### Scenario: Prevent local customization leakage
- **WHEN** the evaluator runs an arm on a machine that has unrelated personal agent customizations
- **THEN** those customizations are absent from the agent under test unless the trial explicitly declares them

#### Scenario: Repeat a comparison
- **WHEN** a trial definition requests multiple repetitions
- **THEN** the system creates a fresh workspace for every repetition and associates each result with the same comparison and its run order

### Requirement: Workflow coexistence contexts
The evaluation system SHALL allow a trial to supply a declared external workflow context independently of Devcraft configuration. It SHALL support verifying that an explicit user workflow choice is honored and that Devcraft does not install, uninstall, disable, or mutate another workflow unless the trial explicitly requests that behavior.

#### Scenario: Honor an explicit workflow choice
- **WHEN** a trial supplies an active OpenSpec context and explicitly directs the agent under test to use OpenSpec
- **THEN** the evaluation can determine whether the agent follows that workflow without detouring through a conflicting Devcraft workflow

#### Scenario: Measure Peters Toolkit overlap
- **WHEN** equivalent trials run with Peters Toolkit only, Devcraft only, and both together
- **THEN** the results expose duplicate phases, conflicting invocations, extra turns, and behavioral differences among the three configurations

### Requirement: Evidence-oriented behavioral fixtures
The initial evaluation corpus SHALL include fixtures for review integrity, cold factual verification, decision evolution, explicit workflow ownership, and Peters Toolkit coexistence. Review-integrity fixtures MUST include both a clean case where empty findings are correct and a seeded-defect case where findings are required.

#### Scenario: Accept a valid empty review
- **WHEN** the agent reviews a fixture with no admissible findings
- **THEN** the verifier rewards an empty findings result and penalizes fabricated findings or quota filling

#### Scenario: Detect real defects without persona dependence
- **WHEN** the agent reviews a fixture containing known admissible defects under persona or seniority framing
- **THEN** the verifier scores the supported defects found and unsupported findings separately without treating the persona as evidence

#### Scenario: Verify facts before finalizing a decision
- **WHEN** a fixture contains load-bearing assumptions whose truth can be checked against available sources
- **THEN** the evaluation determines whether the agent enumerates and verifies those assumptions and changes the decision when material evidence contradicts them

#### Scenario: Preserve decision evolution
- **WHEN** later evidence invalidates the basis for an earlier decision
- **THEN** the evaluation determines whether the agent records the changed basis, the replacement decision, and affected downstream conclusions

### Requirement: Inspectable results and separate measures
The evaluation system SHALL retain the raw transcript or trajectory, final workspace state, verifier output, termination status, timing, and token usage when the host reports it. It SHALL report correctness, false-positive behavior, workflow adherence, and execution overhead as separate measures and MUST NOT hide them behind a single aggregate score.

#### Scenario: Prefer deterministic verification
- **WHEN** a fixture has mechanically checkable outcomes
- **THEN** deterministic checks determine those outcomes independently of any model-based judge

#### Scenario: Use a judge for qualitative behavior
- **WHEN** a criterion cannot be checked mechanically
- **THEN** the system may apply a blinded rubric-based judge while retaining its rubric, input artifacts, and result separately from deterministic checks

#### Scenario: Diagnose an arm difference
- **WHEN** control and treatment outcomes differ
- **THEN** an evaluator can inspect each arm's configuration, transcript or trajectory, verifier details, duration, and reported token use

### Requirement: Safe handling of credentials and external state
The evaluation system MUST keep credentials out of committed fixtures and result artifacts. The Claude OAuth token MUST be passed only through Harbor's runtime secret environment, and the Codex authentication file MUST be supplied only through Harbor's native `CODEX_AUTH_JSON_PATH` transport without exposing the user's broader agent home. A sandboxed host-side authentication-status command MUST NOT substitute for verification inside the actual Harbor agent environment. Trials MUST default to no external mutation beyond their disposable environment and SHALL declare required model endpoints, source hosts, or other network access explicitly.

#### Scenario: Sanitize a captured result
- **WHEN** an agent event stream contains a credential or authentication material supplied at runtime
- **THEN** the persisted result omits or redacts that material

#### Scenario: Block undeclared external mutation
- **WHEN** an agent attempts to modify an undeclared external system during a trial
- **THEN** the environment blocks the action or the trial fails without granting additional authority
