### auditing-tests
- id: bostonaholic:auditing-tests; source path: skills/engineering/auditing-tests/SKILL.md
- description: "Audits a test suite, or a named part, for low-value tests and marks each retain, fix, consolidate, or delete with verified removal evidence. Read-only. Use when the user says "audit the tests", or when asked to audit tests for redundant, junk, or low-value tests. Not for code complexity; use auditing-complexity."
- use when: A suite, or a named path or subsystem, has grown redundant or low-value tests (the agent writes a test per function, several layers replay one contract) and you want to know which can go before anyone deletes one. It inventories every test file in scope, runs the suite once for a baseline, splits the files into lanes by production owner, and gives every test declaration one mark: R retain, F fix the assertion, C consolidate into a named owner, D delete. A delete needs seven evidence fields (location, origin in history, the bug it catches, non-test callers, the remaining stronger proof, code freed, risk and a command). Across lanes it names the keeper suite where several guard one contract. Each C and D then goes to an independent verifier that has not seen the auditor's reasoning and tries to refute "another test still catches this bug"; refuted, inconclusive or incomplete candidates are downgraded to retain. Keeps on doubt, including against the user's own wish to delete.
- not for: making the removals (it edits, deletes, stages and commits nothing; the report is the stop point, and `audit-tests` in dzhng-skills is the variant that edits); judging or rewriting one test while writing it (`principle-test-behavior-not-implementation` in pstack is a passive rule applied one test at a time: redundant tests all pass it, so it removes none); writing tests first or agreeing seams (`tdd` in mattpocock-skills, `tdd` in pstack, `test-driven-development` in superpowers); a flaky or failing test (`diagnosing-bugs`; a test failing in the baseline is kept as a possible product bug); a whole-repo quality audit that only counts untested risky code (`ponytail-audit`).
- needs: a runnable test command for the baseline (without one it says every mark rests on reading alone); git history for each test's origin (a delete whose origin has no history stays retained, so a shallow clone yields few deletions); `node` to run its `scripts/render-report.mjs`, which validates the report and is the only way `report.md` is produced (without it the reply names the command and says the report is unrendered); fresh-context read-only subagents for the lanes and the verifier (without them it works inline and says the verification was not independent). Model-invocable: "audit the tests" may load it unasked. Cost grows with the suite: lanes of at most 25 test files, one verifier claim per C and D.
- side effects: runs the project's test suite once, with whatever that suite itself does. Writes `report.json` and `report.md` to `docs/plans/<YYYY-MM-DD>-auditing-tests/` under the repository root, or to `--out <dir>`: two new untracked files in the working tree. No test or source file is changed. Its description's "Read-only" means the code and tests, not the report directory.
- part of: standalone; it calls no other skill, and its two shared rule files are copied inside the skill directory. Its description points to the uncurated `auditing-complexity` for code complexity.

### audit-tests
- id: dzhng:audit-tests; source path: skills/review/audit-tests/SKILL.md
- description: "Audit whether tests earn their maintenance cost and which suite owns each contract. Use when pruning redundant tests, investigating implementation coupling or test-only production hooks, reviewing the value of proposed coverage, or auditing an entire subsystem. Use write-tests to implement the resulting test changes."
- use when: You want redundant tests pruned, not only reported, one production responsibility at a time. It asks of each test "what bug would escape if this disappeared?", records a disposition with evidence (keep, repair, combine, remove) before any edit, picks the suite that will own each contract, then, when implementation is in scope, moves unique cases into that suite before removing their old home, deletes test-only hooks and support code in the same batch, and proves preservation by breaking the behaviour to see the surviving test fail. An audit-only request stops at the evidence and a proposed batch. For a whole subsystem it inventories every test and gives every declaration a disposition, and an independent reviewer compares removed coverage with its new owners.
- not for: a report with nothing changed and each removal refuted independently before it is offered (`auditing-tests` in bostonaholic-skills: it writes a report and stops, and its verifier and renderer are fixed steps; here the check on removals comes after the edits); judging one test while writing it (`principle-test-behavior-not-implementation` in pstack, one test at a time, removes no redundant ones); test-first work (`tdd` in mattpocock-skills or pstack, `test-driven-development` in superpowers); a failing test (it keeps the claim and investigates the product; `diagnosing-bugs` is the debugger).
- needs: this collection's `write-tests` (how unique cases are carried over and falsified) and `review` (its closing step, which in turn sequences `refactor-change`, `code-review` and `write-docs`), linked by relative path: install them with it, or it stops being self-contained past the evidence stage. A runnable test command and git history. Subagents help a subsystem sweep but are optional. Model-invocable.
- side effects: with implementation in scope it edits and deletes test files, fixtures and test-only production hooks, updates test discovery and CI registration when suites move, and temporarily changes production code to falsify a test, then restores it. It does not say to commit or push. Audit-only: none.
- part of: the review group of dzhng-skills; hands test writing to `write-tests` and close-out to `review`.

### intent-framed-agent
- id: pskoett-ai-skills:intent-framed-agent; source path: skills/intent-framed-agent/SKILL.md
- description: "Frames coding-agent work sessions with explicit intent capture and drift monitoring. Use when a session transitions from planning/Q&A to implementation for coding tasks, refactors, feature builds, bug fixes, or other multi-step execution where scope drift is a risk."
- use when: The agent drifts during multi-step coding work and you want it caught while it happens, not found in review. Worth installing only for multi-step work, and the skill itself says to skip trivial edits. As implementation starts it prints an Intent Frame (outcome, approach, constraints as out-of-scope boundaries, success criteria, size) taken from the request or approved plan, asking only about a decision that would materially change the work and needing no confirmation round for a clear request. During the work it checks at natural boundaries (before a new file or area, before a new unit of work, when an action feels tangential) and, on drift, prints an Intent Check asking whether this is a deliberate pivot or scope creep; an unintended one returns to scope. It closes with an Intent Resolution (fulfilled, partial, pivoted or abandoned; what was delivered; open items). User prohibitions carry across frames.
- not for: a user who wants less ceremony: it adds three short structured blocks per task and a question on each suspected drift, so for small work name nothing; checking finished work against a spec or issue (`code-review` in mattpocock-skills, spec axis, flags scope creep after the fact; `requesting-code-review` in superpowers); a one-off restatement the user compares themselves (`in-your-own-words` in pstack restates the goal once and monitors nothing); a goal that has changed and needs re-interviewing (`grill-with-docs` in mattpocock-skills, which writes glossary and ADR files; this skill only re-frames in chat); holding back over-building (`ponytail` limits how much code is written, not whether the work is still the work asked for); research, planning-only, documentation-only or admin work (the skill excludes them).
- needs: nothing: no CLI, credential or file. Model-invocable: its description triggers on any move from planning to implementation, so an installed copy may frame work the user did not ask to frame. The drift check is the agent judging itself against its own frame: an instruction, not an enforced gate. Optional companions change its behaviour when installed: it invokes `session-context` (prior-session search) after the first frame, and `context-surfing` reads the frame.
- side effects: none on disk; the frame, checks and resolution are chat output only. It runs `entire status` once when a shell is available and continues silently on failure. Installed through the plugin, the plugin's hooks also run (family `plugin` line).
- part of: the inner loop of pskoett-ai-skills (`plan-interview`, then this, `session-context`, `context-surfing`, `verify-gate`, `simplify-and-harden`, `self-improvement`); works alone.
